# Project structure & reorg design — feature colocation (decided) + structural critique of the project split

**Status: DRAFT / brainstorm — nothing moved, no code changed.**

Supersedes and folds in `docs/superpowers/plans/drafts/2026-07-04-file-organization-brainstorm.md`.
That doc's Option B is **decided** (§3 restates it as the settled reorg). The new work here is §4:
a structural critique of how the projects themselves are shaped — naming, cross-project linking,
and the embedded-resource machinery — with everything on the table including the project split.
Pitched at contracts/boundaries/invariants, not prescribed code.

---

## 1. Problem & goals

Two problems, one decided and one open:

1. **(Decided — the reorg.)** Feature scatter + a hand-maintained 40-entry flat
   `<EmbeddedResource>` list. Answering "how does the Switch/Case builder work?" today means
   visiting 8 directories across 3 projects; adding a marker means hand-editing a *different
   project's* csproj and copy-pasting a `LogicalName` prefix. Option B from the prior brainstorm
   fixes both: **feature becomes the primary axis** across the runtime tree, the generator tree,
   and the test tree (mirrored paths), and the flat resource list collapses to **role-convention
   globs** (`Surface/`, `InjectedOnly/`, `EmitHelpers/`) that compute `LogicalName`. §3 restates it.

2. **(Open — this doc's main work.)** Do the *projects themselves* still make logical sense?
   Three flagged smells: (a) namespaces don't match project names, and package names cross over
   assembly names; (b) files linked/removed across projects; (c) files embedded as resources
   from a sibling project. §4 investigates each with citations and takes a position.

**North star (unchanged):** open one folder → see the whole feature. Csproj wiring should
*express* the injection design (roles, prefixes), not enumerate its instances. Everything must
preserve the invariants in §1.1.

### 1.1 Invariants — the acceptance bar for every proposal in this doc

Any structural option below is evaluated against these; each option's verdict explicitly shows
how it satisfies or violates them.

- **I1 — Zero-dependency consumer.** A consumer of the `Synto` generator package needs no runtime
  package reference; generated code stays self-contained. (Roslyn does not propagate an
  analyzer's NuGet deps into the consumer's compilation — `Directory.Build.targets:13-15`
  states this is why the surface is injected as source, not shipped as a lib.)
- **I2 — netstandard2.0 / Roslyn 5.0 analyzer.** The generator ships under `analyzers/dotnet/cs`
  (`Directory.Build.targets:43-47`), TFM netstandard2.0 (`src/Synto.SourceGenerator/Synto.SourceGenerator.csproj:4`),
  Roslyn-5.0 floor (`.claude/playbook/architecture.md:28`).
- **I3 — Single source of truth.** Markers/helpers are authored once in `src/Synto`, embedded and
  rewritten at inject time; the generator never re-declares them (`.claude/playbook/principles.md:59-62`).
- **I4 — LogicalName / byte contract.** Every `Synto.Runtime.*` / `Synto.RuntimeGenerated.*` /
  `Synto.Helper.*` resource name survives byte-identically (or the change owns the snapshot
  rename). Generator-internal types never leak into injected surface or generated output
  (`.claude/playbook/architecture.md:99-102`).
- **I5 — Snapshots pin output shape.** No changes to generated bytes, public namespaces, or
  package identity (`Synto` / `Synto.Core` / `Synto.Diagnostics` — a fixed three-package model,
  `.claude/playbook/principles.md:41-43`).

### 2.3 Embedded-resource wiring — the three delivery channels

`src/Synto.SourceGenerator/Synto.SourceGenerator.csproj` hand-lists **40 resources** in three
prefix groups; every consumer of a group enumerates or hard-codes those names:

| Group | Count / csproj lines | Consumer | Mechanics |
|---|---|---|---|
| `Synto.Runtime.*` | 28, lines 43-78 | `Shared/SurfaceInjectionGenerator.cs` — enumerates the manifest and filters by prefix (`ResourcePrefix`, line 62) | parsed, `public`→`internal` (`PublicToInternalRewriter`, line 116), injected at post-init (line 77) so `[Template]` is discoverable in the same pass; hint = name minus prefix (line 128) |
| `Synto.RuntimeGenerated.*` | 2, lines 92-93 | same generator, shift group (line 70) | `Shared/EquatableArray.cs` / `DiagnosticInfo.cs` are **compiled into the generator AND embedded**; namespace retargeted `Synto` → `Synto.Generators` on injection (`NamespaceShiftRewriter`, line 121). Byte-load-bearing: no leading trivia may be added (csproj:87-90) |
| `Synto.Helper.*` | 10, lines 105-114 | `Templating/Helpers/FileLocalHelpers.cs` — hard-coded per-helper constants (lines 40-49) + `nameof`-anchored scan keys (lines 61-70) | loaded on demand, rewritten `public` class → `file static class` with no namespace; emitted only into the generated file that actually calls the helper (scan-based; `FileLocalHelpers.cs:27-32`) |

So one physical file in `src/Synto` can be consumed through up to **three channels at once** —
e.g. `Syntax/LiteralSyntaxExtensions.cs` is (1) compiled public API in `Synto.Core`,
(2) embedded as `Synto.Helper.LiteralSyntaxExtensions.cs` (csproj:106) and emitted `file`-scoped
into consumer output, and (3) `<Compile Link>`ed into Bootstrap (`Synto.Bootstrap.csproj:12`).
The **role matrix is the design**; the flat per-file list was merely a bad *encoding* of it.

Why the channels exist at all (the load-bearing why, from the doc-comments):

- Roslyn loads analyzers in an isolated context and does **not** flow their NuGet deps into the
  consumer's compilation; a runtime DLL dependency would force consumers to add a package
  reference — violating I1. So the consumer surface ships as **source**.
- Markers are injected `internal` (not `file`) because consumers reference them from their own
  files and `ForAttributeWithMetadataName` needs `TemplateAttribute` visible across the whole
  compilation (`SurfaceInjectionGenerator.cs:26-30`). `internal` also prevents public-API
  pollution and cross-assembly collisions (`architecture.md:82-85`).
- Helpers are emitted `file`-scoped because an injected `internal` copy would be CS0121-ambiguous
  with `Synto.Core`'s public copies when a consumer references both (`SurfaceInjectionGenerator.cs:31-38`,
  `FileLocalHelpers.cs:17-21`).
- Embedding+rewriting (instead of re-declaring in the generator) is what enforces I3: the
  injected copy *cannot* drift from `Synto.Core`'s definition (`SurfaceInjectionGenerator.cs:19-24`).

## 3. The decided reorg — Option B, restated crisply

**Direction (settled):** feature is the primary axis in all three trees — `src/Synto`,
`src/Synto.SourceGenerator`, `test/Synto.Test` — with **mirrored paths**. The pipeline *core*
keeps its stage folders (`Discovery/`, `Analysis/`, `Pipeline/`, `Quoting/` — the 2026-06-30
structure); *plug-in features* (Builders, Decorations, Staging) get pulled out into per-feature
folders. Inside `src/Synto`, per-file roles are expressed by **leaf role folders** —
`Surface/` (compile + inject), `InjectedOnly/` (embed-only, never compiled into `Synto.Core`),
`EmitHelpers/` (compile + emit `file`-scoped) — and the two csprojs shrink to role globs that
*compute* `LogicalName`:

```xml
<EmbeddedResource Include="..\Synto\**\Surface\*.cs"      LogicalName="Synto.Runtime.%(Filename)%(Extension)" />
<EmbeddedResource Include="..\Synto\**\InjectedOnly\*.cs" LogicalName="Synto.Runtime.%(Filename)%(Extension)" />
<EmbeddedResource Include="..\Synto\**\EmitHelpers\*.cs"  LogicalName="Synto.Helper.%(Filename)%(Extension)" />
<!-- shift group stays explicit: 2 dual-role, byte-load-bearing files -->
```

and `src/Synto/Synto.csproj:38-55`'s five removes become one `<Compile Remove="**\InjectedOnly\*.cs" />`.
In the *runtime* tree namespaces do **not** move — the public surface is a contract (§4.1 item 1a),
so its `Synto.*` namespaces stay put regardless of folder depth; every Phase 1 move is
compile-neutral and byte-neutral. (Folder = namespace *does* apply in the generator tree — Phase 2.)

**Phased migration** (each phase independently green; gates from the prior brainstorm):

- **Phase 0 — the one naming exception.** `Templating/Staging/Template.Parameter.cs` currently
  maps to `Synto.Runtime.Template.cs` (`Synto.SourceGenerator.csproj:48`); under the glob it
  would rename. Decide: rename the physical file to `Template.cs` (preferred — zero contract
  movement) or keep a single explicit override. Tiny standalone commit.
- **Phase 1 — runtime role folders + globs.** `git mv` ~30 files inside `src/Synto` into
  `Surface/`/`InjectedOnly/`/`EmitHelpers/` leaves; replace the 40-entry list + 5 removes with
  the globs above; update the 3 Bootstrap link paths (`Synto.Bootstrap.csproj:12-14`).
  **Gate:** full build + suite, zero `.received.` files (`SurfaceInjectionTest`,
  `InjectedSurfaceCompletenessTest`, `ZeroCollisionTest`, `HelperContractTests` pin the bytes),
  packed nupkg layout unchanged.
- **Phase 2 — generator feature folders + namespace alignment.** Pull Builders/Decorations/Staging
  pieces out of `Discovery/`/`Analysis/`/`Quoting/NodePipeline/` into their feature folders **and
  align the internal namespaces to the new folders** (§4.1 item 1: folder = namespace for the
  generator's `internal` pipeline). Target names + full tree in §7 (compiler-phase naming:
  `BindingTime`/`Quoting/Passes`/`Emit`/`Prelude`/`Facades`/`Incremental`). This is now a deliberate `namespace`/`using` rewrite, not a pure
  `git mv` — but it is all `internal`, never reaches injected/generated output, and is
  compiler-checked end to end. The three contract/semantic exceptions stay pinned: shift-group files
  remain `namespace Synto`, and any `Synto.Generators.*` injected-author surface keeps its contract
  namespace. **Gate:** suite green, no snapshot changes (the I4 leak clause + separate compilation
  guarantee no internal type surfaces in output). Runs after the branch decision (§5).
- **Phase 3 — test colocation.** Move per-feature test classes **together with** their
  `snapshots/` dirs (`UseDirectory("snapshots")` is test-file-relative; the orphan guard is
  path-agnostic). **Gate:** suite green, no re-accepts.
- **Phase 4 — docs.** `refresh-kb` (the KB's `path:line` links churn heavily in Phases 1-3).

Open sub-decisions carried forward from the brainstorm: the plug-in-vs-core line for Phase 2
(judgment call), whether to add an explicit resource-manifest assertion against the glob footgun
(this doc recommends **yes** — §4.3), and sequencing vs `experimental/quote-action-pipeline` (§5).

## 4. Structural critique

### 4.1 Smell 1 — namespaces vs projects vs packages

**The reality (from §2.1):** three distinct layers of naming, each answering to a different master:

1. **Folder = namespace by default; decouple only where a namespace is a *contract*.** The
   status-quo rule was blanket — "folders are organizational only, namespaces are fully decoupled" —
   but that over-generalizes from one real constraint. The decoupling is load-bearing in exactly
   three places; everywhere else folder and namespace should line up so navigation and `using`s agree:
   - **(a) Consumer surface** — `Synto`, `Synto.Templating`, `Synto.Matching`, `Synto.Formatting`.
     A consumer writes `using Synto.Templating;`; these namespaces are a *discoverability contract*,
     authored in `src/Synto.Core` and pinned byte-for-byte by `SurfaceInjectionTest`. They are a
     curated shallow tree *by API design*, deliberately independent of how deep the feature folders
     go — forcing namespace = folder here would deepen and scatter the public API and wreck
     discovery. (This is *not* "keep everything flat": `Templating`/`Matching`/`Formatting` are a
     deliberate shallow tree, just one decoupled from folder nesting.)
   - **(b) Injected generator-author surface** — `Synto.Generators.*` (Interceptors authored
     pre-shifted, the cacheability toolkit shifted at inject time). Same reasoning, different
     audience: generator authors write `using Synto.Generators;`, and the injected bytes are
     snapshot-pinned (I4). Conveniently the `InjectedOnly/` role folder already marks these files,
     so "InjectedOnly ⇒ namespace is a contract, not folder-derived" falls out for free.
   - **(c) Shift-group files** (`EquatableArray.cs`, `DiagnosticInfo.cs`) — authored `namespace
     Synto`, retargeted to `Synto.Generators` on injection; the namespace carries load-bearing
     meaning and must be declared explicitly against the folder default.
   Everywhere else — the generator's own `internal` pipeline and the whole test tree — **folder =
   namespace**. Those types never ship as referenceable API and never appear in injected/generated
   output, so aligning them is snapshot-neutral, I4/I5-safe, and compiler-checked. Verdict:
   *codify the refined rule in `architecture.md`* — "folder = namespace, except the three
   contract/semantic cases above" — a tighter, more navigable rule than blanket decoupling.

2. **One genuine footgun: `<RootNamespace>Synto</RootNamespace>`**
   (`Synto.SourceGenerator.csproj:5`). Every hand-written file in that project declares
   `Synto.Generators[.*]` explicitly — *except* the two shift-group files, where `namespace Synto`
   carries **semantic meaning** ("this file is injected downstream under a retargeted namespace",
   csproj:81-90). A newly added file that trusts the IDE default silently lands in `namespace
   Synto`, i.e. accidentally adopts shift-group semantics for a file that isn't in the shift
   group. Fix: set `RootNamespace` to `Synto.Generators` (independent, one-line, branch-safe — do
   it now). Cost ~zero (all LogicalNames are explicit or computed; nothing else keys off
   RootNamespace). Verify gate: build + suite, no resource-name drift. This is a stepping stone:
   the project rename in item 3 (`src/Synto.SourceGenerator` → `src/Synto.Generators`) makes
   `RootNamespace` match the dir and retires the footgun for the right reason — a file trusting
   the default then lands in the *correct* root, and only the shift-group files declare `namespace
   Synto` against it.

3. **The package↔assembly crossings** (`Synto` package carries `Synto.SourceGenerator.dll` +
   `Synto.dll`; `Synto.dll` *is* the `Synto.Core` package's assembly; and the generator's assembly
   name `Synto.SourceGenerator.dll` matches neither its namespace root `Synto.Generators` nor its
   package `Synto`) are the #1 onboarding confusion and the only naming misalignments that are
   *not* load-bearing. Options:

   | Option | Shape | Invariant check | Verdict |
   |---|---|---|---|
   | **1a — document only** | Add the §2.1 matrix to `architecture.md`; no renames | All hold trivially | Cheapest; leaves the confusion priced in forever |
   | **1b — rename *both* projects to match their namespaces** (`src/Synto` → `src/Synto.Core` → `Synto.Core.dll`; `src/Synto.SourceGenerator` → `src/Synto.Generators` → `Synto.Generators.dll`; both `PackageId`s stay put — `Synto.Core` / `Synto`) | Package identities untouched (I5 ✓ — `PackageId`s already `Synto.Core` / `Synto`). Injected bytes contain **no assembly name** — generated output is self-contained (I1 ✓), so snapshots don't move (I4 ✓). Mechanical touch points: sln; ~6 `ProjectReference` paths across both dirs; `Directory.Build.targets:46,56-58` (hard-codes `Synto.dll` / `MSBuildSourceProjectFile="Synto.csproj"`, plus the generator project/assembly it packs to `analyzers/dotnet/cs`); Bootstrap link paths; test alias + generator refs (`test/Synto.Test/Synto.Test.csproj:89`). **IVT catch:** the Core rename leaves IVT strings alone (`src/Synto/Synto.csproj:64-66` names the *friends*, not itself), but the *generator* rename changes a friend name — Core's `InternalsVisibleTo("Synto.SourceGenerator")` → `"Synto.Generators"`. Package-internal layout (`analyzers/dotnet/cs/*.dll`) is consumer-invisible; Roslyn loads by directory | **Recommended**, sequenced *last* (§5): every layer reads straight — dir = assembly = namespace-root for both — and the *only* remaining crossing is the deliberate marketing one: `Synto.Generators.dll` ships inside the package named `Synto` (flagship gets the bare name) |
   | **1c — rename packages to match projects** | Violates I5 outright (`principles.md:41-43`: package identity is a contract) | **Rejected** |

   A half-measure (rename a dir but pin `<AssemblyName>` back to the old name) just moves the
   mismatch down a level; if 1b is done, do it fully — dir, assembly, and namespace root together.

**Position:** the refined folder=namespace rule (item 1) stays; kill the RootNamespace footgun now
(independent, one-line); do the *paired* 1b rename (`src/Synto` → `Synto.Core` **and**
`src/Synto.SourceGenerator` → `Synto.Generators`) as a standalone commit after everything else, or
consciously choose 1a — this is Open Question 1.

### 4.2 Smell 2 — cross-project linking (and its shadow: duplication)

**Stated policy (user):** cross-project file-linking is acceptable **only in `src/Synto.Bootstrap`**
— it never ships, carries a deliberately lower quality bar, and any breakage fails every
build/test loudly (it generates part of `src/Synto`'s quoter; `Synto.csproj:75`).

**Finding: the codebase already complies.** The complete inventory (§2.2) shows the only
cross-project `<Compile Include>` links in the repo are Bootstrap's three
(`Synto.Bootstrap.csproj:12-14`). The five `<Compile Remove>` entries in `Synto.csproj:38-55`
are *intra*-project role flags, not links, and Option B Phase 1 replaces them with one
role-folder glob. After Phase 1 the policy is satisfied by construction: no per-file link/remove
entries anywhere, three sanctioned Bootstrap links (paths updated, mechanism unchanged).

**The real residue is duplication-as-linking-avoidance** — and it needs a *policy decision*,
because the written guidance currently contradicts itself:

1. **The quoter pair** (`src/Synto/Quoting/CSharpSyntaxQuoter.cs` ↔
   `src/Synto.Bootstrap/CSharpSyntaxQuoter.cs`). The in-file SYNC NOTEs on both sides declare
   the copies intentional ("intentionally a separate copy … not a linked file",
   `src/Synto/Quoting/CSharpSyntaxQuoter.cs:17-18`); `architecture.md:103-106` says the opposite
   ("prefer a shared/linked file so they can't diverge"). Note these are **not** copies of one
   program: the runtime side is an abstract base whose other half is *generated by Bootstrap*
   (241 lines), the Bootstrap side is a self-contained visitor that quotes the runtime quoter
   (202 lines, different base, uses `Bootstrap.Helpers`). A single linked source would be
   conditional-compilation soup (the `BOOTSTRAP` define, `Synto.Bootstrap.csproj:8`, exists but
   is unused for this). What must stay in sync is not the *text* but the **per-node-kind
   coverage**, and the Bootstrap snapshot test already guards exactly that.
   **Position: bless the duplicate.** Keep separate copies + snapshot guard; fix
   `architecture.md:103-106` to match the in-file notes (the doc drifted, not the code). This
   also happens to be the one place the user's linking exception *would* permit a link — declining
   it is a choice about which failure mode is worse (silent `#if` divergence vs. loud snapshot
   divergence), and the snapshot wins.

2. **The cacheability-toolkit triplication** (`EquatableArray` + `DiagnosticInfo`/`LocationInfo`
   in `Synto.SourceGenerator/Shared/`, `Synto.Diagnostics/`, `Synto.Bootstrap/`; §2.2). Each
   non-canonical copy carries a `<remarks>` declaring deliberate self-containment. Options:

   - **2a — link from `Shared/` into Diagnostics/Bootstrap.** Violates the user's linking policy
     for Diagnostics (Bootstrap would be allowed). Also couples the "separate product"
     (`principles.md:16-18`) to the umbrella generator's source tree. Rejected for Diagnostics.
   - **2b — dog-food the injection**: have `Synto.Diagnostics` reference the `Synto` generator
     as an analyzer and consume the injected `Synto.Generators.EquatableArray` — the *exact
     mechanism Synto ships to third-party generator authors*. Structurally elegant (Synto would
     eat its own cooking), but it inverts the product boundary: `Synto.Diagnostics` must stay
     independent of the syntax toolkit (`principles.md:16-18`) and it would add a build-order
     edge from the umbrella generator into the diagnostics product. Worth noting as the shape a
     *post-GA* world might choose; rejected now (I5-adjacent: it entangles two package products).
   - **2c — keep 3 copies, add a mechanical clone-sync guard**: a trivial test that reads the
     three files, normalizes namespace + the self-description `<remarks>`, and asserts textual
     equality (same style as `ZeroCollisionTest` — cheap, loud, no build coupling). The copies
     are ~60 lines each and today differ only in namespace + remarks (verified by diff). **Recommended.**

   Invariant check for 2c: no bytes ship differently (I4/I5 ✓), no dependencies added (I1 ✓),
   single-source-of-truth is *approximated* by the guard rather than enforced by MSBuild — an
   explicit, documented trade in exchange for keeping Diagnostics a genuinely standalone product.

3. **`SymbolExtensions` pair** (`src/Synto/Symbols/SymbolExtensions.cs` ↔
   `src/Synto.Bootstrap/SymbolExtensions.cs`, 32 vs 38 lines). Inside the Bootstrap exception;
   either convert to a fourth `<Compile Link>` (allowed by policy, removes a copy) or leave.
   Low stakes; fold the decision into the Phase 1 commit that already touches Bootstrap's link paths.

### 4.3 Smell 3 — embedding files as resources from a sibling project

**The mechanism, precisely** (§2.3 has the full wiring): the zero-dependency invariant (I1)
forces the consumer surface to travel as *source inside the generator assembly*; the
single-source-of-truth invariant (I3) forces that source to be *the same files* that compile
into `Synto.Core`. The intersection of those two forces is: **files authored in one project,
embedded into another, rewritten at inject/emit time** (`public`→`internal` for markers,
`public`→`file` for helpers, namespace-shift for the generator-author toolkit). Given the
dual-ship requirement — the same types must exist as public compiled API in `Synto.Core` *and*
as injected internal source via `Synto` — some cross-project bridge is unavoidable. The question
is only which bridge.

**Options evaluated:**

- **3a — status quo shape + Option B role globs (recommended).** Embedding stays declared in the
  generator's csproj, but as three role globs instead of 40 hand-typed entries. The complaint
  "adding a marker means editing a different project's csproj" **dissolves entirely** — adding a
  marker becomes "drop the file in the feature's `Surface/` folder", zero csproj edits. And
  there is a positive cohesion argument for keeping the embedding declaration on the generator
  side: the resource manifest is part of the **generator's** contract — the prefix constants and
  enumeration logic live in generator code (`SurfaceInjectionGenerator.cs:62,70`,
  `FileLocalHelpers.cs:38-49`), and the generator is the sole consumer of the manifest. The
  csproj that declares the resources sits next to the code that reads them.
  Invariants: I1-I5 all hold; LogicalNames computed identically (I4), modulo the Phase 0
  exception which the plan owns explicitly.
  *Residual risk (the glob footgun):* dropping a file into a role folder ships it into every
  consumer with no reviewable csproj diff. Mitigation: a **manifest-pinning test** — assert the
  exact expected resource-name set of the generator assembly, so adding surface produces a
  readable list-diff in review, not just a Verify approval. Recommended (answers the prior
  brainstorm's Q2 with *yes*).

- **3b — a dedicated "surface source" project** (shared-project/source-only tree that `Synto.Core`
  compiles and the generator embeds). Superficially cleaner ownership ("the surface has a home"),
  but: it adds a fifth project node that produces no assembly (or a `.shproj`, with poor modern
  tooling); the role distinction (`Surface` vs `InjectedOnly` vs `EmitHelpers`) still has to be
  expressed *inside* it — i.e. the same leaf folders, one indirection further away; and it
  **fights the decided feature-colocation axis** — builders' markers would leave
  `src/Synto/Templating/Builders/` for a parallel surface tree, recreating the two-roots wart
  Option B just killed. Invariants hold (I1-I5 ✓) but the north star doesn't. Rejected.

- **3c — split `src/Synto` into `Synto.Core` (surface) + `Synto.Toolkit` (quoter machinery).**
  The machinery (`CSharpSyntaxQuoter`, `SyntaxFormatter`, `UsingDirectiveSet`, extensions) is
  `internal` today and consumed only by the generators via IVT (`Synto.csproj:58-67`) — so why
  does it live in a shipped runtime package at all? Two reasons it should stay: (1) the
  **self-host chain** targets it — Bootstrap generates `CSharpSyntaxQuoter.Generated.cs` *into*
  `src/Synto` (`Synto.csproj:75`), so the machinery's home is where the generated half lands;
  (2) the quoter engine is deliberately **public-shaped and slated to flip public at GA** (the
  middleware-quoter work kept it `internal`/public-shaped precisely so `Synto.Core` can expose
  it) — i.e. the machinery is *future consumer surface*, not misplaced generator code. Splitting
  now is speculative structure for a boundary that GA will redraw anyway
  (`principles.md:79`: no speculative abstraction). Invariants: would hold (I1-I5 ✓) but adds a
  package-identity question (I5 risk if `Synto.Toolkit` ships). **Rejected now; revisit at
  quoter GA** — the GA flip is the natural moment to re-ask what `Synto.Core` is.

- **3d — merge `src/Synto` into `src/Synto.SourceGenerator`** (two-project model). Proven out by
  the invariants, not just by fiat: (i) `Synto.Core` is a shipped standalone package — merging
  kills a package identity (**I5 violation**) or forces one assembly packed into two products;
  (ii) today, **separate compilation is itself the enforcement mechanism for I4's leak clause**:
  an embedded surface file that references a generator-internal type *fails `Synto.Core`'s
  build*, because those types don't exist in that compilation. Merge the projects and that
  compile-time fence disappears — surface purity would demote from "enforced by the compiler"
  to "checked by tests"; (iii) the self-host ordering (Bootstrap → `Synto` → generator) would
  entangle the umbrella generator in the bootstrap chain for no benefit. **Rejected; the split
  is forced.**

- **3e — move the resource declarations into `src/Synto` itself** (embed the surface into
  `Synto.dll`'s manifest; the generator reads the *referenced* assembly's resources —
  `Synto.dll` already ships beside the generator under `analyzers/dotnet/cs`,
  `Directory.Build.targets:46`, and is loaded at analysis time). This is the strongest
  alternative: the authoring project would own its own embedding, and `LogicalName` globs would
  live one directory away from the files. Invariants: I1-I3 hold; I4 holds if names are computed
  identically; I5 holds (injected bytes unchanged). Costs: `Synto.Core`'s *lib* nupkg carries
  dead resources for its direct consumers; `SurfaceInjectionGenerator`/`HelperResourceLoader`
  switch from `typeof(...).Assembly` self-enumeration (bulletproof) to cross-assembly resource
  loading (a new failure mode in exotic analyzer-load configurations); and the wiring moves
  *away* from the prefix constants and enumeration code that define the contract (§3a's cohesion
  argument, inverted). Post-Option-B, the friction 3e would remove is already gone (no csproj
  edit per file). **Verdict: viable but not worth it now** — note it as the fallback if the glob
  convention ever proves insufficient.

**Position:** the embedding machinery is not a workaround — it is the *direct, minimal
expression* of I1 ∧ I3 under the dual-ship requirement. What was wrong was the encoding (a flat
instance list), and Option B fixes the encoding. Adopt 3a + the manifest-pinning test; keep 3e
in the back pocket; re-open 3c only at quoter GA.

## 7. Target tree & folder naming

This section pins the concrete post-reorg layout and the folder *names*. Applied only to the
generator and test trees (Phase 2-3); the `Synto.Core` layout is §3's role folders unchanged. All
of it is internal (`folder = namespace` for the generator — §4.1 item 1), so it is snapshot-neutral
and compiler-checked; naming is taste, not invariant risk.

### 7.1 Naming principle

Synto *is* a quasiquotation compiler — its public verbs `Quote` / `Unquote` / `Splice` are Lisp
quasiquotation (`quote` / `,` / `,@`). So the internal folders inherit that lineage rather than
inventing jargon. The generator tree reads front-to-back as a compiler:
**Discovery → BindingTime → Quoting (+ Passes) → Staging → Emit**, with `Facades`/`Decorations` as
self-contained feature folders and `Prelude` as the emitted standard library. The junk-drawer names
(`Shared`, `Helpers`, `Builders`) are retired.

| Today | Target | Lineage / why |
|---|---|---|
| `Shared/` (equatable models + symbol glue) | `Incremental/` | Roslyn incremental-generator equatable-model caching (the *why* they exist) |
| `Shared/SurfaceInjectionGenerator.cs` | generator **root** | it is a top-level `IIncrementalGenerator`, peer to the two feature drivers — not "shared" infra |
| `Templating/Analysis/` | `Templating/BindingTime/` | partial evaluation — *binding-time analysis* (Jones/Gomard/Sestoft) |
| `Templating/Helpers/` | `Templating/Prelude/` | Haskell/ML "prelude" — the library implicitly available to emitted code |
| `Templating/Builders/` | `Templating/Facades/` | the code's own `Facade*` nouns; GoF façade — it generates facades, not "builders" |
| `Quoting/NodePipeline/` + `ListPipeline/` | `Quoting/Passes/` | compiler *passes*; Roslyn `CSharpSyntaxRewriter` |
| `Templating/Pipeline/` | `Templating/Emit/` | Roslyn `Emit` back end; the output factory is the *residual program* (partial evaluation). `NameAllocator` here is **gensym** (Lisp hygiene) |
| `Discovery/`, `Staging/`, `Lifting/`, `Diagnostics/`, `Matching/` | *unchanged* | already domain-accurate — `Lifting` = cross-stage persistence, `Staging` = MetaML/MetaOCaml multi-stage programming |

`Synto.Core` keeps its names: they already track Roslyn's own namespaces (`Syntax/`, `Symbols/`,
`Formatting/`) plus domain verbs (`Quoting/`, `Templating/`, `Matching/`, `Decorations/`). Core keeps
**`Builders/`** for the public `[SyntaxBuilder]` marker surface — deliberately *not* `Facades/`: the
asymmetry is honest (Core ships the public *builder* markers; the generator holds the *facade* that
implements them).
